===  Service Group - Telemetry (SERVICEGROUP_ID: 0x0011)

In general, telemetry refers to the automated collection of various on-chip and
on-board metrics from distributed/remote sources and their transmission to a
central system for monitoring and analysis of system health and usage,
troubleshooting system issues and optimization of performance/resources.

The RPMI Telemetry service group aims to assist system-level telemetry. It
defines a set of services that allow application processors to obtain various
system-level data from platform microcontrollers.

The group also serves sensors which will be accessed purely from the sensors
standpoint and not from the system-level telemetry perspective.

==== Introduction

This section introduces a few terms/concepts and associated details that are
used within the RPMI Telemetry service group, as follows:

===== Telemetry Data Element

An independent measurable property of a platform or system is captured by an
entity termed as a Telemetry Data Element (abbreviated as TDE).

Each TDE is identified by a 32-bit integer value in the range `[0, N - 1]`,
where `N` is the number of TDEs supported by the RPMI Telemetry service group,
as reported by the `TELEMETRY_GET_ATTRIBUTES` service. The description of
various attributes of a TDE can be obtained iteratively using the
`TELEMETRY_GET_TDE_ATTRIBUTES` service.

For example, CPU temperature, GPU voltage, NPU power, Memory size are different
TDEs. The value of some TDEs can come from an associated physical sensor, while
the value of other TDEs can be runtime register values, software counters, or
aggregated values.

TDEs includes sensors providing simple scalar values like voltage, temperature
or they can be multi-axis sensors which can provide data values along more than
one axes like IMU which can combine accelerometer, gyroscope, magnetometer.

Each axis of a multi-axis sensor functions as an independent sensor and hence
it should be represented as a separate TDE. Each axis specifies its own unit of
measurement and other attributes. A sensor reporting uncalibrated values can
report bias estimates as additional axes of measurement.

One of the TDE attribute defines its purpose - simple sensor control,
configuration & access or telemetry information.

- Component and Type can further have instances where an instance is a
  sequentially increasing number starting from `0`. When there is only 1
  instance available for a Component/Type, its instance value is fixed to `0`.
- For a multi-CPU system, CPU instances hence are `0`, `1`, etc. Each CPU can
  measure different entities, such as voltage and temperature, which can be
  captured at multiple physical points.
- For example, consider a platform with multiple CPU instances, where CPU
  instance `2` has two voltage sensing points, each represented as a separate
  Telemetry Data Element (TDE). Both TDEs have `Component` set to `CPU` and
  `Type` set to `Voltage`. Component Instance `2` identifies CPU2, while Type
  Instance values `0` and `1` distinguish the individual voltage sensing
  points.

===== Telemetry Data Capture Mode

Each TDE will capture its data in one of the mode listed in the following table:

[#table-data-capture-mode]
.Data Capture Mode
[cols="2, 4, 7a", width=100%, align="center", options="header"]
|===
| Value | Description | Comments

| 0x00 | Unspecified | -
| 0x01 | Cumulative | Successive additive value since the data capture started
| 0x02 | Continuous | Instantaneous value obtained at each sampling interval
| 0x03 | Spot | Instantaneous value obtained at next sampling interval
| 0x04 | Average | Average of all the values since the data capture started
| 0x05 | State | ON/ OFF or active/ inactive
| 0x06 | Counter | Sequential count value since the data capture started
| 0x07-0x7F | Reserved for future use | -
| 0x80-0xFF | OEM or Implementation defined | -
|===

A TDE whose purpose is just sensor configuration and access, will mostly be
capturing data in Spot or Continuos mode only.

===== Telemetry Shared Memory Region

The size of the Telemetry shared memory region including all the TDEs must be a
multiple of 4KB. The `size` (in bytes) and `base-address` of this region can be
discovered using the `TELEMETRY_GET_ATTRIBUTES` service. The `base-address`
must also be aligned to 4KB.

The offset of the TDEs and their respective size in the shared memory region
can be discovered using the `TELEMETRY_GET_TDE_ATTRIBUTES` service. The offsets
of different TDEs in the shared memory must be aligned to 4 bytes. The TDE's
offset when added to the `base-address` of the Telemetry shared memory region
gives the address from where a particular TDE area begins.

The Telemetry shared memory region is owned by the platform microcontroller.
The data producer (i.e., the platform microcontroller) will be the one writing
this region with telemetry or sensor data, while the application processor will
be the consumer reading telemetry or sensor data from the shared memory region.

===== Telemetry Data Element Data Unit

A TDE's data value as per its Type will be in some unit like `Watts`, `Ampere`,
etc. and this unit can be derived from the formula

====
[stem]
++++
dataUnit = baseUnit \times 10^{unitModifier} rateUnit
++++
====

The baseUnit can be chosen from Table 75 - Sensor Units enumeration as defined
in the DMTF DSP0248 (Platform Level Data Model for Platform Monitoring and
Control Specification) cite:[DMTF].

For example, if baseUnit is `Volts` and the unitModifier is `-6`, then unit of
the data value returned is `microvolts`. unitModifier's or exponent's value is
in two's complement format and acts as the power-of-10 multiplier. If the
rateUnit property is set to a value other than None, the units are further
qualified as rate units. In the preceding example, if rateUnit is set to `per
second`, then the value returned is in `microvolts/second`.

===== Telemetry Data Element Data Format

The `TELEMETRY_GET_ATTRIBUTES` service indicates whether the RPMI Telemetry
group supports timestamps via the `TS_CTR_FREQ` value. A TDE further indicates
its timestamp support via the `TELEMETRY_GET_TDE_ATTRIBUTES` service. There can
be scenarios in which the Telemetry group supports timestamps, but not all TDEs
provide timestamped data values.

Accordingly, a TDE's shared memory content will be as per one of the following
data formats:

===== Telemetry Data Group

For common control and configuration, different TDEs which can be sampled at
common interval, can be clubbed together inside a data collection group called
Telemetry Data Group (abbreviated as TDG).

Each TDG is identified by a 32-bit integer value in the range `[0, M - 1]`,
where `M` is the number of TDGs supported by the RPMI Telemetry service group,
as reported by the `TELEMETRY_GET_ATTRIBUTES` service. The description of
various attributes of a TDG can be iteratively obtained using the
`TELEMETRY_GET_TDG_ATTRIBUTES` service.

Each TDE MUST be a part of one and only one TDG.

It makes sense to group all axes of a multi-axis sensor together in a single
TDG and nothing else should be part of that TDG.

It is further recommended to group the various TDEs of a multi-axis sensor in
their natural order like X, Y, Z-axis. How does it effect?

[#sampling-interval-format-section]
===== Sampling Interval Format

Sampling interval of a TDG is the interval after which the data for all its
constituent TDEs can be sampled and is represented by the formula
====
[stem]
++++
samplingInterval = baseVal \times 10^{unitModifier}
++++
====

Here, baseVal is a value in `seconds` and unitModifier's or exponent's value is
in two's complement format and acts as the power-of-10 multiplier. So, a
sampling interval is a word/32-bit value defined as follows:

[#table-sampling-interval-word]
.Sampling Interval Word
[cols="1, 4", options="header"]
|===
| Bits
| Description

| [31:24]
| Must be `0`.

| [23:8]
| Base value in `seconds`.

| [7:0]
| Unit modifier's value in two's complement format.
|===

====== Linear Range Format

A linear range of sampling intervals represented by minimum and maximum

structure of linear sampling interval range:

```c

```

.Linear Sampling Interval Range Structure
[cols="1, 3, 5" width=100%, align="center", options="header"]
|===
| Word
| Name
| Description

| 0

| 1
| SAMPLING_INTERVAL_MAX
| Maximum sampling interval in `seconds`.

| 2
| SAMPLING_INTERVAL_STEP
| Step size between two successive sampling intervals in `seconds`.
|===

A TDG may also support sampling intervals which can be represented by multiple
linear ranges. For example,
```c
[sampling_interval_min0, sampling_interval_max0, sampling_interval_step0],
[sampling_interval_min1, sampling_interval_max1, sampling_interval_step1],
 ...,
[sampling_interval_min(N-1), sampling_interval_max(N-1), sampling_interval_step(N-1)]
```
The linear ranges must be packed sequentially such that
`sampling_interval_max0 < sampling_interval_min1`,
`sampling_interval_max1 < sampling_interval_min2` and so on.

[#telemetry-notifications]
==== Notifications

This service group does not support any events for notification.

==== Service: TELEMETRY_ENABLE_NOTIFICATION (SERVICE_ID: 0x01)

This service allows the consumer to subscribe to RPMI Telemetry service group
notifications. The platform may optionally support notifications for events
that may occur. The provider can send notification messages to the consumer if
they are implemented and the consumer has subscribed to them.

The supported events are described in <<telemetry-notifications>>.

Refer to <<table_common_ennotification_request_data>> for Request Data and
<<table_common_ennotification_response_data>> for Response Data.

It would be desirable to support events to avoid wastage of CPU cycles at the
AP level. This would be required for trip events in case of a sensor and also
for a sensor which is a bit slow in terms of providing its data. Thus, this
will enable asynchronous operational mode with events. Presently, asynchronous
operational mode is supported, but AP needs to poll the TDE's Sequence Counter.

A sensor supporting trip-point will generate a TELEMETRY_EVENT_TRIP_POINT when
its scalar value crosses the configured threshold. Multi-axis sensors can also
optionally support trip-points only if all the axes report their values in same
units. In such a case, TELEMETRY_EVENT_TRIP_POINT is generated when value on
any axis crosses the configured threshold.

==== Service: TELEMETRY_GET_TDG_SAMPLING_INTERVALS (SERVICE_ID: 0x06)

This service is used to get the sampling intervals supported by a TDG. The
cumulative number of sampling intervals and their format returned depend on the
corresponding values reported by the `TELEMETRY_GET_TDG_ATTRIBUTES` service.

If the format is discrete, the message can pass the `INTERVAL_INDEX`, which is
the index of the first sampling interval value to be described in the returned
sampling intervals array. Similarly, if the format is linear range, then
`INTERVAL_INDEX` is the index of the first linear range to be described in the
returned sampling interval linear range list. To obtain all supported discrete
sampling interval values or linear ranges, the first index value has to be `0`.

The total number of words required for the number of discrete sampling
intervals or linear ranges according to the format in one message must not
exceed the total words available in a message DATA field. If the format is
linear range and a TDG supports multiple linear ranges, then only complete
linear ranges must be returned as per the data format of the linear range
described in <<sampling-interval-format-section>>.

If the total number of words required to store all supported discrete sampling
intervals exceed the available words in message DATA field, then `REMAINING`
and `RETURNED` fields must be set accordingly. If the format is discrete, then
the platform microcontroller will set the `RETURNED` field to number of
discrete sampling intervals that can be accommodated in one message and the
`REMAINING` field is set to the remaining number of discrete sampling
intervals. Similarly, if the format is linear, the `RETURNED` field is set to
the number of linear ranges that can be accommodated in one message and the
`REMAINING` field is set to the remaining number of linear ranges.

The application processor, must call this service again and again with
appropriate `INTERVAL_INDEX` set to get the discrete sampling intervals or
linear ranges till the `REMAINING` field is not `0`.

==== Service: TELEMETRY_TDG_START (SERVICE_ID: 0x07)

This service is used to initiate or start the capture of TDG's data as per the
desired configuration. The offsets in shared memory where data for the
constituent TDEs is provided are the same as those reported by the
`TELEMETRY_GET_TDE_ATTRIBUTES` service for those TDEs. It is the client's
responsibility to provide the correct number of implementation-specific
configuration words and their values via this service.

When this service is invoked, the Data Sequence Counter of the constituent TDEs
begins with `0` and it continues to flow normally thereafter as per subsequent
updates. In a continuous data capture scenario, any wraparound of a TDE's Data
Sequence Counter is expected to be handled by the client.

NOTE: As long as a TDE's Data Sequence Counter remains at its initial value of
      `0`, it means there is no data yet for that TDE. This does not apply in
      the case of a wraparound. Refer <<tde-data-format>> for details.

For a sensor only TDG, the trip-point event configuration can be specificed
through the configuration words parameter (may be we can drop the word
implementation from implementation-specific and can term it as group-specific
words) which for such a TDG are not actually required to be first specified/
obtained through the `TELEMETRY_GET_TDG_ATTRIBUTES` service.

One configuration word specifying ID of the trip event and its direction would
be required. Two other words will be needed to define the trip-point low and
high 32-bit values. The TDG_START call will serve as trip-point enablement call
and TDG_STOP call serves the trip-point disablement.

As the trip-point configuration is through this service, a TDG must not have
multiple scalar sensor TDEs unless all can support same configuration and same
number of trip points. For a multi-axis sensor, all axes having the same sensor
type must support same number of trip points and same trip-point configuration.
